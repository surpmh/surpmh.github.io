1-1.인앱결제 서버 검증으로 위변조와 중복 지급 차단

  • 전체적인 아키텍처
    클라이언트의 결제 결과가 아니라 스토어 거래 원장을 기준으로 지급합니다.
  • 문제 원인
    • 앱이 보내는 “결제에 성공했다”는 신호를 그대로 신뢰하는 구조였습니다. 앱은 조작 가능한 실행 환경이라 결제 없이 성공 응답을 만들어 보낼 수 있습니다.
    • 성공한 영수증을 그대로 여러 번 전송하면 지급이 반복됩니다.
    • 같은 영수증이 동시에 들어오면 중복 확인과 잔액 갱신 사이에 경쟁 상태가 생깁니다.
    • 환불과 취소는 스토어에서 일어나는데 서버가 알 방법이 없어 수기로 확인해야 했습니다.
  • 해결 과정
    • 서버 사이드 영수증 검증 — Google Play Developer API와 App Store Server API로 서버가 직접 조회해 결제 사실을 확인합니다. 신뢰 경계를 앱 바깥의 스토어 원장으로 옮겼습니다.
    • 재전송 차단을 스키마에 — transaction_id에 UNIQUE 제약을 걸어 애플리케이션 조건문이 아니라 DB 제약이 중복을 막게 했습니다. 호출 경로가 늘어도 빠뜨릴 수 없습니다.
    • 지급 갱신 구간 직렬화 — SELECT ... FOR UPDATE로 유저 행을 잠가 동시 요청에서도 순차 처리를 보장했습니다.
    • 환불 자동 반영 — Google RTDN과 App Store Server Notifications를 수신해 환불과 취소를 서버 상태에 자동 반영했습니다.
  • 결과
    • 위변조와 재전송 결제를 서버에서 차단
    • 운영 기간 중 중복 지급 0건 유지
    • 구글과 애플 결제를 동일한 검증 인터페이스로 통합해 플랫폼 분기를 결제 로직 밖으로 분리
    • 환불과 취소가 자동 반영되어 수기 대응 제거

1-2.반복되던 서버 OOM 장애의 원인별 대응

  • 전체적인 아키텍처
    가공하는 계층을 애플리케이션에서 DB로 옮긴 사례 1의 구조 변화입니다.
  • 문제 원인
    • 운영 중 서버 메모리가 계속 올라가다 OOM Kill로 프로세스가 강제 종료되는 장애가 여러 차례 반복됐습니다. 증상은 매번 같았지만 원인은 건마다 달랐습니다.
    • 공통적으로 직전 배포가 없었습니다. 코드가 그대로인데 증상이 새로 생겼다면 시간에 따라 변하는 조건, 즉 데이터 누적을 원인 축으로 잡아야 했습니다.
    • 사례 1 — 여러 테이블을 각각 통째로 조회한 뒤 애플리케이션 메모리에서 Join과 GroupBy로 가공하는 패턴이었습니다. 최종 응답은 작아도 중간 단계에서 원본 전체가 힙에 올라옵니다.
    • 사례 2 — 채팅 기록 조회에서 필터 조건과 ORDER BY 순서가 인덱스 컬럼 구성과 어긋나 있었습니다. 데이터가 적을 때는 전체 스캔 비용이 감당되다가, 누적량이 임계를 넘은 시점에 한 번의 요청이 방대한 행을 메모리에 올렸습니다.
  • 해결 과정
    • 메모리를 점유하는 주체부터 특정 — 추측으로 코드를 고치지 않고 후보 엔드포인트를 반복 호출하며 메모리 사용량 변화를 관찰했고, 메모리 덤프로 실제 힙 점유 객체를 확인했습니다.
    • 사례 1: 가공을 DB 쿼리 레벨로 이관 — 조인과 집계를 SQL에서 처리하고 서버는 이미 좁혀진 결과만 받도록 바꿨습니다. 힙에 올라오는 양이 전체 데이터량이 아니라 응답 크기에 비례하게 됩니다.
    • 사례 2: 조회 패턴 기준 복합 인덱스 재설계
      • EXPLAIN으로 해당 조회가 전체 스캔으로 떨어지는 것을 먼저 확인했습니다.
      • WHERE가 항상 (user_id, character_id)이고 정렬이 created_at이었으므로 그 순서의 복합 인덱스로 필터와 정렬을 하나로 커버했습니다.
      • 인덱스는 쓰기 비용을 늘리므로 조회 패턴이 확인된 컬럼에만 적용했습니다.
    • 조회량의 상한을 서버가 결정 — 목록 조회가 요청이 요구하는 만큼이 아니라 서버가 정한 상한 안에서 응답하도록 했습니다.
  • 결과
    • 두 건 모두 동일 원인의 OOM이 재발하지 않았고 서버 메모리 사용량이 안정화
    • 사례 2는 EXPLAIN 기준 접근 방식이 전체 스캔에서 인덱스 range 스캔으로 전환
    • 데이터가 늘어도 해당 요청이 점유하는 메모리가 그에 비례해 늘지 않게 됨
    • 증상이 아니라 원인 단위로 접근하는 방식을 이후 장애 대응의 기본으로 삼음

1-3.간헐적 응답 지연의 원인을 DB 설정에서 찾아 무중단 해소

  • 전체적인 아키텍처
  • 문제 원인
    • API 응답이 간헐적으로 수 초씩 지연되고 앱 최초 실행 로딩도 유독 느리다는 증상이 있었습니다.
    • 느린 쿼리를 의심했지만 같은 쿼리를 다시 실행하면 정상 속도로 돌아왔습니다. 느린 쿼리가 아니라 같은 쿼리가 어떤 때는 느리고 어떤 때는 빠른 문제였습니다.
    • DB를 관리형 서비스가 아니라 EC2에 직접 구성해 운영했기 때문에 DB 서버 설정과 자원도 직접 관리 대상이었고, innodb_buffer_pool_size가 MySQL 기본값 128MB로 남아 있었습니다.
    • 누적 데이터 대비 버퍼 풀이 턱없이 작아 자주 읽는 데이터조차 메모리에 머물지 못하고 매번 디스크로 밀려나는 상태였습니다.
  • 해결 과정
    • 재현 조건에서 출발 — 처음 실행되거나 오랜만에 실행되는 쿼리만 느리고 직후 재실행은 빠르다는 패턴을 확인해, 쿼리가 아니라 데이터를 어느 계층에서 읽는가의 문제로 정리했습니다.
    • 인스턴스 메모리 사전 확인 — DB가 EC2에서 직접 운영 중이었으므로 가용 메모리를 먼저 확인하고 애플리케이션과 OS 몫을 제외한 범위에서 5GB로 잡았습니다.
    • 서비스 중단 없이 적용 — innodb_buffer_pool_size는 동적 변경이 가능한 파라미터라 재시작 없이 반영하고, 재부팅 후에도 유지되도록 설정 파일에 함께 기록했습니다.
  • 결과
    • 간헐적으로 수 초씩 걸리던 콜드 쿼리 지연과 앱 첫 진입 로딩 지연 해소
    • 자주 읽는 데이터가 메모리에 머물게 되어 같은 쿼리의 응답 시간이 실행 시점과 무관하게 일정해짐
    • 서비스 중단 없이 적용
    • 기본값으로 남아 있는 설정 자체를 점검 대상으로 보게 됨

1-4.요청과 실행을 분리한 AI 이미지 생성 파이프라인

  • 전체적인 아키텍처
  • 문제 원인
    • 이미지 생성은 사내 AI팀 API를 호출해 처리했고 한 건에 30초 정도가 걸렸습니다. 요청을 받으면 그 자리에서 생성 API를 호출하는 구조였습니다.
    • 요청이 들어오는 만큼 30초짜리 외부 호출이 그대로 늘어나 동시 실행 수에 상한이 없었습니다. 스레드와 커넥션이 묶이고 외부 API 호출 제한에도 걸립니다.
    • 진행 중인 작업이 서버 메모리에만 존재해 재배포나 재시작, 예외가 나면 그대로 사라졌습니다. 사용자는 완료 알림을 받지 못합니다.
    • 실패가 어디에도 기록되지 않아 무엇이 왜 실패했는지 알 수 없었고, 환불 같은 후속 처리의 근거도 남지 않았습니다.
  • 해결 과정
    • 접수와 실행의 분리 — API는 생성 요청을 대기 상태로 저장만 하고 끝냅니다. 실제 호출은 스케줄러가 담당합니다.
    • 상태를 저장소에 남김 — PENDING → PROCESSING → DONE / FAILED로 관리해 서버가 중간에 내려가도 재시작 후 이어서 처리할 수 있게 했습니다.
    • 동시 실행 수의 상한 — 스케줄러가 한 번에 정해진 개수만 꺼내 처리합니다. 요청이 몰려도 외부 API 동시 호출 수는 서버가 정한 값을 넘지 않습니다.
    • 실패의 후속 처리 — 생성 실패는 재시도하지 않고 환불로 처리했습니다. 대상을 특정할 수 있어야 하므로 실패도 결과의 한 종류로 기록했습니다.
  • 결과
    • 생성 작업이 요청 처리 자원을 점유하지 않게 되어 외부 API의 지연과 장애가 다른 API로 번지지 않도록 격리
    • 요청이 몰려도 외부 API 동시 호출 수가 서버가 정한 상한을 넘지 않음
    • 서버가 재시작돼도 대기 중이거나 처리 중이던 요청이 남아 있어 작업이 유실되지 않음
    • 실패한 작업이 상태로 남아 환불 처리와 원인 파악이 가능

1-5.목록 조회의 N+1 쿼리 제거

  • 전체적인 아키텍처
    왕복 횟수를 목록 건수에서 떼어내는 것이 이 작업의 목표였습니다.
  • 문제 원인
    • 목록 API가 느리다는 제보가 있었습니다. 목록 자체는 한 번의 쿼리로 가져오고 있었지만, 각 항목의 대표 이미지를 붙이는 코드가 반복문 안에서 항목 한 건마다 이미지 테이블을 다시 조회하고 있었습니다.
    • 목록이 N건이면 쿼리가 1 + N회 나갑니다. 개별 쿼리는 각각 빠르므로 느린 쿼리를 찾는 방식으로는 원인이 잡히지 않습니다.
    • 지연이 데이터의 총량이 아니라 한 화면에 보여주는 건수에 비례합니다. 목록을 더 많이 내려줄수록 선형으로 느려집니다.
    • 정렬과 상위 한 건 추출이 await 뒤에 있어 DB가 아니라 애플리케이션에서 동작했습니다. 한 건만 쓰면서 해당 항목의 이미지를 전부 전송받고 있었습니다.
  • 해결 과정
    • 비례 관계부터 확인 — 특정 데이터에서만 느린 것이 아니라 목록 건수를 늘릴수록 응답이 함께 늘었습니다. 쿼리 한 번의 비용이 아니라 횟수가 비용이라고 판단했습니다.
    • 선행 수집 후 일괄 조회 — 목록에서 식별자를 먼저 모으고 IN 조건으로 이미지를 한 번에 가져왔습니다.
    • 딕셔너리로 매핑 — 가져온 이미지를 식별자로 그룹지어 사전에 담고, 각 항목은 조회 없이 사전에서 꺼내 씁니다. 최신 한 건 선택은 그룹 안에서 처리했습니다.
    • 인덱스 정렬 — (항목 식별자, 상태, 등록일시) 순서의 복합 인덱스로 필터와 정렬을 인덱스 하나로 커버하게 했습니다.
  • 결과
    • DB 왕복이 1 + N회에서 2회로 고정되어 목록 건수와 무관해짐
    • 목록을 더 많이 내려줘도 응답 시간이 건수에 비례해 늘지 않음
    • 요청 하나가 커넥션을 잡고 있는 시간이 줄어 동시 요청 상황에서의 여유 확보
    • 목록을 다루는 코드에서 응답 크기와 함께 이 코드가 만드는 쿼리가 몇 번인지를 보게 됨

2-1.AWS에서 GCP로 API 서버 이전

  • 전체적인 아키텍처
    변경 지점을 애플리케이션 계층 한 곳으로 좁히고 DNS 전환을 마지막에 두었습니다.
  • 문제 원인
    • 회사가 GCP 크레딧을 지원받게 되면서 운영 비용 절감을 위해 API 서버를 옮겨야 했습니다. 성능 개선이 아니라 실행 환경만 바꾸는 작업이었습니다.
    • 이전 작업은 옮길 것이 많을수록 실패 지점이 늘어납니다. 애플리케이션과 DB를 함께 옮기면 문제가 생겼을 때 어느 쪽 때문인지 가려내기 어렵습니다.
    • 운영 중인 서비스이므로 이전 후 동작이 달라지거나 중단되면 그대로 장애가 됩니다.
  • 해결 과정
    • 이전 범위를 좁힘 — 데이터베이스는 이전 대상에서 제외하고 애플리케이션 계층만 옮겨 변경 지점을 한 곳으로 만들었습니다.
    • 검증을 전환보다 먼저 — 새 환경에서 기존 데이터베이스 연결과 응답 동작을 먼저 확인한 뒤에 트래픽을 옮겼습니다.
    • DNS 전환을 마지막에 — 레코드 전환을 마지막 단계에 두어 문제가 생기면 되돌릴 수 있는 상태를 유지했습니다.
  • 결과
    • 이전 이후 기능 차이나 운영 장애 없이 서비스 유지
    • 크레딧 활용으로 운영 비용 절감
    • 전환 실패 시 되돌릴 경로를 확보한 상태로 작업 완료

2-2.Jenkins에서 GitHub Actions로 배포 파이프라인 통합

  • 전체적인 아키텍처
  • 문제 원인
    • CI/CD가 별도 서버로 운영되는 Jenkins에 묶여 있었습니다. 코드는 GitHub에, 배포 설정은 Jenkins 서버에 나뉘어 있어 배포 흐름을 한곳에서 볼 수 없었습니다.
    • 빌드 서버 자체가 유지 대상이자 장애 지점이었습니다. 서버가 죽으면 배포가 막힙니다.
  • 해결 과정
    • 배포 정의를 저장소로 이동 — 빌드와 배포 절차를 워크플로 파일로 옮겨 코드와 같은 저장소에서 버전 관리되게 했습니다.
    • 기존 배포 절차를 그대로 옮긴 뒤 정리 — 동작이 달라지지 않도록 먼저 같은 결과를 내게 하고, 확인이 끝난 다음 불필요한 단계를 걷어냈습니다.
  • 결과
    • 배포 프로세스를 저장소 중심으로 단일화해 빌드 서버를 따로 유지할 필요가 없어짐
    • 배포 설정이 코드와 함께 버전 관리되어 변경 이력이 남음

3-1.유니티 클라이언트와 응답 규격을 먼저 합의한 API 설계

  • 전체적인 아키텍처
  • 문제 원인
    • 게임 콘텐츠 API의 응답 형태를 서버가 단독으로 정하고 있었습니다.
    • 규격이 어긋나면 이미 양쪽 구현이 끝난 연동 단계에서 드러납니다. 그 시점의 수정은 서버와 클라이언트를 함께 되돌려야 해서 비용이 큽니다.
    • 특히 예외 상황의 응답 형태에서 인식 차이가 생기기 쉬웠습니다.
  • 해결 과정
    • 설계 단계에서 규격 합의 — 유니티 클라이언트 개발자와 응답 규격과 예외 처리 방식을 먼저 맞춘 뒤 구현에 들어갔습니다.
    • 예외를 규격의 일부로 — 정상 응답뿐 아니라 실패 응답의 형태와 처리 방식까지 합의 대상에 포함했습니다.
    • 이벤트 웹은 양쪽 모두 담당 — 룰렛과 빙고, 뽑기 등 인앱 이벤트 웹페이지는 백엔드와 React 프론트엔드를 함께 개발했습니다.
  • 결과
    • 연동 단계에서 규격이 어긋나 되돌리는 일을 줄임
    • API를 쓰는 쪽의 사정을 설계에 반영하는 방식으로 협업 기준을 잡음

3-2.랭킹 조회 캐싱으로 반복 집계 쿼리 제거

  • 전체적인 아키텍처
  • 문제 원인
    • 랭킹 조회가 요청마다 집계 쿼리를 실행하고 있었습니다.
    • 그런데 랭킹은 변경 빈도가 낮고 모든 회원이 같은 결과를 봅니다. 같은 계산을 요청 수만큼 반복하는 셈이었습니다.
    • 집계 쿼리는 단건 조회보다 비싸서 조회가 몰리면 DB 부하로 이어집니다.
  • 해결 과정
    • 캐싱 대상 선별 — 회원마다 결과가 다른 데이터가 아니라, 모두가 같은 결과를 보고 변경 빈도가 낮은 랭킹을 대상으로 골랐습니다.
    • Redis에 10분 TTL — 랭킹은 실시간 정확도보다 응답 속도가 중요한 데이터라고 보고, 최신성을 일부 양보하는 대신 TTL로 갱신 주기를 명시했습니다.
  • 결과
    • 매 요청마다 반복되던 집계 쿼리를 제거해 데이터베이스 부하 감소
    • 조회가 몰려도 집계 실행 횟수가 TTL 주기에 묶여 요청 수와 무관해짐
