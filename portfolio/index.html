CASE 01 · PAYMENT

서버가 직접 검증하는 인앱결제 처리 구조

// invariant  — 지급은 스토어가 검증해준 거래에만 일어난다

클라이언트가 보낸 결제 결과를 신뢰하지 않고 스토어 원장(Google과 Apple)을 소스 오브 트루스로 삼아 위변조와 재전송을 차단하고, 환불과 취소는 스토어 서버 알림으로 자동 반영

Problem

인앱결제에서 앱이 보내는 “결제에 성공했다”는 신호를 그대로 신뢰하면 세 가지 사고가 발생합니다.

  • 위변조 — 결제하지 않고도 성공 응답을 만들어 서버에 보낼 수 있습니다.
  • 재전송(replay) — 성공한 영수증을 그대로 여러 번 보내면 지급이 반복됩니다.
  • 동시 요청 — 같은 영수증이 동시에 들어오면 중복 체크와 잔액 갱신 사이에 경쟁 상태가 생깁니다.

Architecture

Solution

  • 서버 사이드 영수증 검증 — 앱의 결제 결과를 신뢰하지 않고 Google Play Developer API와 App Store Server API를 통해 영수증을 서버에서 직접 검증합니다.
  • 환불 자동 반영 — 환불과 취소 상태 변경을 스토어의 서버 알림(Google RTDN과 App Store Server Notifications)으로 수신해 수기 대응 없이 서버 상태를 스토어와 정합하게 유지합니다.
  • transaction_id UNIQUE 제약 (멱등성) — 재전송이 들어와도 DB 제약에서 차단됩니다. 애플리케이션 로직이 아니라 스키마가 중복을 막게 했습니다.
  • 비관적 락 — 결제 빈도가 높진 않아 경쟁이 잦진 않았지만 잔액 갱신 구간에 SELECT … FOR UPDATE로 유저 행을 잠가 동시 요청에서도 순차 처리를 보장했습니다.

Result

  • 앱이 보낸 결제 결과를 신뢰하지 않고 스토어 원장에서 직접 검증하는 구조로, 위변조와 재전송 결제를 서버에서 차단했습니다.
  • Google과 Apple 양쪽 결제를 동일한 검증 인터페이스로 통합해 플랫폼별 분기를 결제 로직 밖으로 밀어냈습니다.
  • 환불과 취소를 스토어 서버 알림으로 자동 반영해, 수기 대응 없이 서버 상태와 스토어 상태를 일치시켰습니다.
  • 재전송을 DB 제약에서 차단하고 지급 갱신 구간을 행 락으로 직렬화해, 운영 기간 중 중복 지급 0건을 유지했습니다.

What I learned

결제는 “성공했다”는 신호를 믿는 일이 아니라 서버가 검증하는 일이라는 것을 배웠습니다. 그리고 중복 방지 같은 불변식은 애플리케이션 조건문보다 DB 제약처럼 우회할 수 없는 층에 두는 편이 훨씬 안전하다는 것도 함께 배웠습니다.

CASE 02 · ASYNC PIPELINE

요청과 실행을 분리한 AI 이미지 생성 파이프라인

// invariant  — 진행 중인 작업은 서버가 죽어도 사라지지 않는다

요청 즉시 실행하던 30초짜리 외부 호출을 대기열로 옮겨, 동시 실행 수의 상한을 서버가 정하고 재시작에도 작업이 유실되지 않도록 전환

Problem

이미지 생성은 사내 AI팀이 제공하는 API를 호출해 처리했고, 한 건에 30초 정도가 걸렸습니다. 요청을 받으면 그 자리에서 생성 API를 호출하고, 완료되면 S3에 업로드한 뒤 소켓으로 클라이언트에 알리는 구조였습니다. 클라이언트는 기다리지 않았지만, 서버 쪽에는 문제가 남아 있었습니다.

  • 요청이 들어오는 만큼 30초짜리 외부 호출이 그대로 늘어나 동시 실행 수에 상한이 없었습니다. 스레드와 커넥션이 묶이고 외부 API 호출 제한에도 걸립니다.
  • 진행 중인 작업이 서버 메모리에만 존재해, 재배포나 재시작, 예외가 나면 그대로 사라졌습니다. 사용자는 완료 알림을 영영 받지 못합니다.
  • 실패가 어디에도 기록되지 않았습니다. 무엇이 왜 실패했는지 알 수 없으니, 사용자에게 후속 처리를 해줄 근거도 남지 않습니다.

Architecture

Solution

  • 접수와 실행의 분리 — API는 생성 요청을 대기 상태로 저장만 하고 끝냅니다. 실제 호출은 스케줄러가 담당합니다.
  • 상태를 저장소에 남김 — PENDING → PROCESSING → DONE / FAILED로 관리해, 서버가 중간에 내려가도 재시작 후 이어서 처리할 수 있게 했습니다.
  • 동시 실행 수의 상한 — 스케줄러가 한 번에 정해진 개수만 꺼내 처리합니다. 요청이 몰려도 외부 API 동시 호출 수는 서버가 정한 값을 넘지 않습니다.
  • 실패의 후속 처리 — 생성 실패는 다시 시도하지 않고 환불로 처리했습니다. 어떤 요청이 실패했는지가 상태로 남아야 대상을 특정할 수 있으므로, 실패도 결과의 한 종류로 기록했습니다.

Result

  • 생성 작업이 요청 처리 자원을 점유하지 않게 되어, 외부 API의 지연과 장애가 다른 API로 번지지 않도록 격리됐습니다.
  • 요청이 몰려도 외부 API 동시 호출 수가 서버가 정한 상한을 넘지 않게 됐습니다.
  • 서버가 재시작돼도 대기 중이거나 처리 중이던 요청이 남아 있어 작업이 유실되지 않습니다.
  • 실패한 작업이 상태로 남아 환불 처리와 원인 파악이 가능해졌습니다.

What I learned

비동기로 만들었다고 해서 안정적인 것은 아니라는 걸 배웠습니다. 응답을 먼저 돌려주더라도 실행이 메모리에만 남아 있으면 서버가 죽는 순간 함께 사라집니다.

“요청과 실행을 분리한다”는 말의 핵심은 응답 속도가 아니라, 실행의 결과를 성공이든 실패든 확인할 수 있는 형태로 남겨두는 것이었습니다.

CASE 03 · INCIDENT & MEMORY

메모리 덤프로 좁힌 OOM — 애플리케이션에서 하던 가공을 쿼리로

// invariant  — 데이터를 합치고 묶는 일은 DB가 하고, 서버는 결과만 받는다

메모리가 치솟아 OOM Kill로 종료되던 장애 중 한 건 — 여러 테이블을 각각 조회해 애플리케이션 메모리에서 Join과 GroupBy 하던 패턴을 덤프 분석으로 특정하고 DB 쿼리 레벨로 이관

Problem

서버 메모리가 계속 올라가다 OOM Kill로 프로세스가 강제 종료되는 장애가 운영 중 반복됐고, 발생할 때마다 원인이 달랐습니다. 이 케이스는 그중 데이터를 가공하는 위치가 원인이었던 건입니다. 직전 배포가 없어 배포 이력에는 단서가 없었고, 어떤 요청이 메모리를 점유하는지부터 특정해야 했습니다.

Diagnosis

  • 의심 엔드포인트에 반복 요청 — 메모리 증가와 상관관계가 있는 요청을 찾기 위해 후보 엔드포인트를 반복 호출하며 사용량 변화를 관찰했습니다.
  • 메모리 덤프 분석 — 어떤 객체가 힙을 점유하는지 덤프로 확인해, 추측이 아니라 실제 점유 주체를 근거로 범위를 좁혔습니다.
  • 가공 위치가 원인 — 여러 테이블을 각각 통째로 조회한 뒤 애플리케이션 메모리에서 Join과 GroupBy로 가공하는 패턴이었습니다. 최종 응답은 작아도, 중간 단계에서 원본 데이터 전체가 힙에 올라오는 구조였습니다.

Solution

  • 가공을 DB 쿼리 레벨로 이관 — 조인과 집계를 SQL에서 처리하고, 서버는 이미 좁혀진 결과 집합만 받도록 바꿨습니다. 인덱스와 옵티마이저를 쓸 수 있는 계층에서 처리하게 한 것입니다.
  • 중간 결과의 크기를 데이터 증가와 분리 — 힙에 올라오는 양이 전체 데이터량이 아니라 응답 크기에 비례하도록 만들었습니다.

Result

  • 동일 원인의 OOM이 재발하지 않았고, 서버 메모리 사용량이 안정화됐습니다.
  • 데이터가 늘어도 해당 요청이 점유하는 메모리가 그에 비례해 늘지 않게 됐습니다.

What I learned

같은 결과를 만들더라도 어느 계층에서 가공하느냐가 자원 사용량을 결정한다는 것을 배웠습니다. 애플리케이션에서 하는 조인은 코드로는 자연스러워 보이지만, DB가 인덱스로 걸러줄 수 있는 일을 서버 메모리로 끌고 오는 선택이었습니다.

그리고 메모리 문제는 추측이 아니라 덤프로 좁혀야 한다는 것도 함께 배웠습니다.

Retrospective

메모리 사용량 추이에 대한 알림이 있었다면 OOM Kill 이전에 대응할 수 있었을 것입니다. 이 건과 다음 CASE 04는 증상(메모리 초과로 인한 프로세스 종료)이 같아도 원인이 전혀 달랐고, 그래서 증상이 아니라 원인 단위로 확인하는 습관이 필요하다는 것을 알게 됐습니다.

CASE 04 · INCIDENT & QUERY

데이터 누적으로 뒤늦게 드러난 조회 결함과 인덱스 재설계

// invariant  — 기록이 쌓여도 한 페이지를 읽는 비용은 늘지 않는다

배포 이력 없는 서버 다운 — 필터와 정렬 순서가 인덱스 구성과 어긋나 전체 스캔 → OOM. 복합 인덱스 재설계로 EXPLAIN 접근 방식이 full scan에서 index range로 전환, 동일 원인 재발 0건

Problem

메모리 초과로 서버가 종료되는 장애는 한 번이 아니었고, 원인도 서로 달랐습니다. 앞선 CASE 03이 가공 위치의 문제였다면, 이 건은 데이터 누적으로 뒤늦게 발현된 조회 결함입니다. 직전 배포도 없었고 코드도 그대로인데 서버가 다운됐습니다. 원인은 채팅 기록 조회였는데, 필터링 자체는 이미 걸려 있었습니다. 문제는 필터 조건과 정렬(ORDER BY) 순서가 인덱스 컬럼 구성과 어긋나 있던 것이었습니다. 그 결과 조회가 인덱스를 타지 못하고 누적된 대화 기록 전체를 훑게 되면서, 한 번의 요청이 방대한 양의 행을 메모리에 올렸고 프로세스가 종료됐습니다.

채팅 기록은 사용자와 캐릭터의 조합마다 계속 누적되는 데이터이고, 조회는 언제나 “특정 사용자의 특정 캐릭터 대화를 최신순으로”라는 형태로 들어옵니다. 이 결함은 처음부터 있었지만 드러나지 않았습니다. 데이터가 적을 때는 인덱스를 타지 못해도 전체 스캔 비용이 감당됐고, 누적량이 임계를 넘은 시점에야 장애로 나타났습니다.

Diagnosis

  • 에러 로그에서 출발 — 프로세스 종료 시점의 로그를 기준으로 어떤 요청 처리 중에 발생했는지 범위를 좁혔습니다.
  • 배포가 아닌 데이터를 의심 — 코드 변경이 없는데 증상이 새로 생겼다는 점에서, 시간에 따라 변하는 조건인 데이터 누적을 원인 축으로 잡았습니다.
  • EXPLAIN으로 실행 계획 확인 — 해당 조회가 인덱스를 타지 못하고 전체 스캔으로 떨어진다는 것을, 필터와 정렬 순서가 인덱스 컬럼 구성과 어긋난 데서 확인했습니다.

Solution

  • 조회 패턴을 기준으로 복합 인덱스 구성 — WHERE 조건이 항상 (user_id, character_id)로 함께 들어오고 정렬은 created_at이었으므로, (user_id, character_id, created_at) 순서로 두어 필터와 정렬을 인덱스 하나로 커버하도록 했습니다.
  • 조회량의 상한을 서버가 결정 — 목록 조회는 요청이 요구하는 만큼이 아니라 서버가 정한 상한 안에서 응답하도록, 한 번에 메모리로 올라오는 행 수를 제한했습니다.
  • 필요한 곳에만 — 인덱스는 조회를 빠르게 하는 대신 쓰기 비용을 늘리므로, 실제 조회 패턴이 확인된 컬럼에만 적용했습니다.

Result

  • EXPLAIN 기준, 해당 조회의 접근 방식이 전체 스캔에서 인덱스 range 스캔으로 바뀌어 페이지당 읽는 행이 요청한 건수 수준으로 좁혀졌습니다.
  • 동일 원인의 서버 다운이 재발하지 않았습니다.
  • 조회 대상이 해당 사용자와 캐릭터 범위로 좁혀져, 전체 데이터 증가가 개별 조회 비용에 그대로 반영되지 않게 됐습니다.

What I learned

테스트 환경에서 통과했다는 것이 안전하다는 뜻은 아니라는 걸 배웠습니다. 결함은 코드가 바뀔 때가 아니라 데이터가 바뀔 때도 드러납니다. 그래서 “지금 정상 동작하는가”보다 “데이터가 100배가 돼도 같은 비용으로 동작하는가”를 함께 확인하게 됐습니다.

인덱스도 많이 거는 게 아니라 조회 패턴에 맞게 거는 것이라는 걸 배웠습니다. 특히 복합 인덱스는 개수보다 컬럼 순서가 사용 가능 여부를 결정하고, 그 확인은 감이 아니라 EXPLAIN으로 해야 한다는 것도 함께 알게 됐습니다.

Retrospective

당시에는 장애가 난 뒤에야 발견했습니다. 조회 건수나 응답 크기에 대한 모니터링 지표가 있었다면 다운 이전에 신호를 볼 수 있었을 것입니다. 또 대용량 데이터를 전제로 한 테스트가 있었다면, 운영 중이 아니라 개발 단계에서 잡혔을 문제였습니다.

인덱스가 필터와 정렬을 함께 커버하더라도, OFFSET 기반 페이징은 뒤 페이지로 갈수록 앞의 행을 읽고 버리는 비용이 커집니다. 데이터가 더 쌓였다면 커서 기반 페이징으로 바꿔, 깊은 페이지에서도 방금 읽은 위치부터 이어가도록 했을 것 같습니다.

CASE 05 · DB TUNING

같은 쿼리인데 가끔만 느리다 — InnoDB 버퍼 풀 증설

// invariant  — 자주 읽는 데이터는 디스크가 아니라 메모리에서 응답한다

간헐적으로 수 초씩 걸리던 API 응답의 원인을 쿼리가 아닌 DB 서버 설정(버퍼 풀 128MB)에서 찾아, 서비스 중단 없이 5GB로 증설해 Cold 쿼리 지연과 앱 첫 진입 로딩 지연을 해소

Problem

API 응답이 간헐적으로 수 초씩 지연되고, 앱을 처음 실행할 때의 로딩도 유독 느리다는 증상이 있었습니다. 느린 쿼리를 의심했지만 같은 쿼리를 다시 실행하면 정상 속도로 돌아왔습니다. 느린 쿼리라기보다, 같은 쿼리가 어떤 때는 느리고 어떤 때는 빠른 문제였습니다.

Diagnosis

  • 재현 조건에서 출발 — 처음 실행되거나 오랜만에 실행되는 쿼리만 느리고, 직후 재실행은 빠르다는 패턴을 확인했습니다. 쿼리 자체가 아니라 데이터를 어디서 읽어오는지의 차이라고 판단했습니다.
  • 디스크 읽기 병목 의심 — 첫 실행은 디스크에서, 재실행은 메모리에서 읽는다면 증상이 정확히 설명됩니다. InnoDB 버퍼 풀 설정을 확인했습니다.
  • 기본값 그대로 운영 중 — 버퍼 풀이 MySQL 기본값 128MB로 운영되고 있었습니다. 누적된 데이터 대비 턱없이 작아, 자주 읽는 데이터조차 메모리에 머물지 못하고 매번 디스크로 밀려나는 상태였습니다.

Solution

  • 인스턴스 메모리 사전 확인 후 증설 — DB가 EC2에서 직접 운영 중이었으므로, 서버의 가용 메모리를 먼저 확인하고 애플리케이션과 OS 몫을 제외한 범위에서 5GB로 잡았습니다.
  • 서비스 중단 없이 적용 — innodb_buffer_pool_size는 동적 변경이 가능한 파라미터라 재시작 없이 반영하고, 재부팅 이후에도 유지되도록 설정 파일에 함께 기록했습니다.

Result

  • 간헐적으로 수 초씩 걸리던 Cold 쿼리 지연과 앱 첫 진입 로딩 지연이 해소됐습니다.
  • 자주 읽는 데이터가 메모리에 머물게 되어, 같은 쿼리의 응답 시간이 실행 시점과 무관하게 일정해졌습니다.

What I learned

느린 응답이 항상 쿼리의 문제는 아니라는 것을 배웠습니다. 같은 쿼리의 첫 실행과 재실행이 다르게 동작한다면 의심할 곳은 SQL이 아니라 데이터가 어느 계층(메모리 / 디스크)에서 읽히는가입니다. 그리고 DB의 기본 설정은 운영 데이터 규모를 알지 못하므로, 기본값으로 돌아가고 있는 설정 자체가 점검 대상이라는 것도 알게 됐습니다.

Retrospective

당시에는 증상이 나타난 뒤에야 원인을 찾았습니다. 버퍼 풀 히트율 (Innodb_buffer_pool_reads / read_requests)을 모니터링 지표로 두었다면 사용자가 지연을 겪기 전에 신호를 볼 수 있었을 것입니다. 또 데이터가 계속 커지면 증설만으로는 한계가 오므로, 오래된 로그성 데이터의 아카이빙처럼 working set 자체를 줄이는 방향도 함께 준비했을 것 같습니다.

CASE 06 · GLOBALIZATION

클라이언트가 언어를 관리하지 않는 다국어 응답 구조

// invariant  — 같은 사용자에게는 어느 클라이언트에서든 같은 언어로 응답한다

Problem

앱과 웹, 백오피스가 각자 번역을 관리하면 서버가 새 에러 코드를 추가할 때마다 모든 클라이언트 배포가 필요해지고, 번역이 누락되면 사용자에게 코드값이 그대로 노출됩니다. 서버에서 처리하더라도 메시지를 반환하는 모든 지점이 언어 분기를 갖게 되면 같은 문제가 코드 안으로 옮겨올 뿐입니다.

Solution

  • 미들웨어에서 언어를 한 번만 판별 — Accept-Language 헤더를 요청 진입 지점에서 해석해, 이후 컨트롤러와 서비스는 언어를 알 필요가 없게 했습니다. 언어 분기가 각 로직으로 번지지 않습니다.
  • 번역 테이블을 단일 소스로 — 메시지를 코드가 아니라 데이터로 관리해, 문구 수정과 지원 언어 추가를 코드 변경 없이 처리할 수 있게 했습니다.
  • 조회 캐싱 — 번역은 거의 모든 응답에서 조회되는 데이터라 매 요청 DB를 거치지 않도록 캐싱했습니다. 대신 수정 반영에는 캐시 갱신만큼의 시차가 생깁니다.
  • 기본 언어 폴백 — 헤더가 없거나 미지원 언어여도 코드값이 그대로 노출되지 않게 했습니다.

Result

  • 세 클라이언트가 동일한 메시지 소스를 참조하게 되어, 문구 수정과 지원 언어 추가가 클라이언트 배포 없이 번역 테이블 수정만으로 반영됩니다.
  • 언어 처리가 미들웨어 한 곳에 모여, 새 메시지를 추가할 때 다국어를 따로 신경 쓰지 않아도 되게 됐습니다.

What I learned

다국어는 번역 파일을 만드는 일이 아니라 어느 계층이 언어를 책임질지 정하는 설계 문제라는 것을 배웠습니다. 언어를 미들웨어로 올리고 메시지를 데이터로 내리자, 나머지 코드가 다국어를 의식하지 않아도 되는 구조가 됐습니다.

OPERATIONS

운영 경험 — 개발자 개입 없이 굴러가는 서비스

어드민 백오피스

운영팀이 콘텐츠와 회원 데이터를 직접 관리하는 백오피스를 개발해, 반복성 운영 요청이 개발자를 거치지 않고 처리되는 환경을 만들었습니다.

회원 인증 체계

카카오와 애플 소셜 로그인과 SMS 본인인증 기반 가입과 로그인(JWT / Refresh Token)을 구현해 인증 전 구간을 담당했습니다.

AI 선톡 · FCM 동적 푸시

OpenAI API로 메시지를 생성하고 회원별 변수를 발송 시점에 치환해 개인화 메시지를 자동 발송했으며, 딥링크와 동적 이미지를 담은 Payload로 다양한 알림 시나리오를 지원했습니다.

Technical Decisions

기술적 의사결정

같은 문제라도 규모와 팀 상황에 따라 답이 달라집니다. 당시 선택의 근거와, 전제가 바뀌면 언제 다른 선택으로 넘어갈지를 함께 기록합니다.

DECISION 01 · CONCURRENCY

분산 락 대신 DB 행 락

상황

결제 지급 갱신 구간의 동시 요청 제어. Redis 기반 분산 락과 DB 비관적 락(SELECT … FOR UPDATE)이 후보였습니다.

판단

  • 분산 락이 필요한 상황은 여러 서버가 DB 밖의 자원을 두고 경합할 때입니다. 당시 문제는 같은 DB 행에 대한 동시 갱신이었고, 이 경합은 DB가 이미 트랜잭션으로 직렬화해 줍니다.
  • 행 락은 트랜잭션과 수명주기가 일치합니다. 커밋과 롤백에 맞춰 해제되므로, 분산 락에서 신경 써야 하는 TTL 만료와 락 유실, 해제 누락 같은 실패 모드가 없습니다.
  • Redis에 락을 두면 정합성의 핵심 구간이 외부 인프라의 가용성에 의존하게 됩니다. 지켜야 할 데이터가 있는 곳(DB)에서 지키는 편이 구조적으로 단순합니다.

전제가 바뀐다면

DB가 샤딩되어 한 지급 처리가 여러 DB에 걸치거나, DB 락 대기가 처리량 병목으로 관측되는 시점이 분산 락 또는 다른 조율 방식을 검토할 기준입니다.

DECISION 02 · QUEUE

메시지 큐 대신 DB 테이블 + 스케줄러

상황

AI 이미지 생성 대기열. 처음에는 메시지 큐 도입을 먼저 떠올렸지만, 필요 조건을 따져보며 DB 기반 대기열로 방향을 잡았습니다.

판단

  • 필요한 것은 버퍼링, 순차 처리, 실패 기록, 그리고 상태 조회였습니다. 이 중 "지금 어떤 작업이 어떤 상태인가"를 들여다보는 운영 가시성은 SQL로 바로 조회되는 DB가 브로커보다 낫습니다.
  • 소비자가 스케줄러 하나뿐이고 처리량도 낮아, 큐가 강점을 갖는 다중 컨슈머 분배나 고처리량 상황이 아니었습니다. 이 조건에서 브로커는 성능 이점 없이 운영과 모니터링, 장애 지점만 추가합니다.
  • 작업 상태가 서비스 데이터와 같은 DB에 있어, 접수와 상태 기록을 하나의 트랜잭션으로 다룰 수 있었습니다.

전제가 바뀐다면

워커를 여러 대로 늘려 작업 분배가 필요해지거나, 폴링 주기가 처리 지연의 병목이 되거나, 처리량이 크게 늘어나는 시점이 메시지 큐로 넘어갈 기준입니다. 도구가 아니라 전환 조건을 먼저 정의해 두는 것이 이 결정에서 배운 점입니다.

DECISION 03 · STORAGE

채팅 로그 저장소로 MongoDB

상황

회원과 캐릭터 조합마다 끝없이 누적되는 채팅 로그의 저장소 선택. 핵심 데이터가 이미 있는 MySQL과 MongoDB가 후보였습니다.

판단

  • 조회가 항상 대화 단위로 들어오고 다른 테이블과의 조인이 필요 없는, 읽기 패턴이 단순한 데이터였습니다.
  • 메시지에 텍스트와 이미지, 시스템 메시지 등 형태가 다른 필드가 섞이고 스키마 변경이 잦아, 문서 모델이 자연스러웠습니다.
  • 쓰기가 append 위주인 로그성 데이터를 분리해, 핵심 트랜잭션 데이터가 있는 MySQL의 부하와 격리했습니다.

Retrospective

당시에는 대화를 큰 단위로 묶어 저장하는 설계를 택했는데, 대화가 길어질수록 문서가 비대해지고 일부 메시지만 다루는 작업의 비용이 커지는 한계가 있었습니다. 다시 설계한다면 메시지 단위 문서 + (user, character, created_at) 인덱스로 두어, 대화 길이와 무관하게 읽기와 쓰기 비용이 일정한 구조를 택할 것입니다. 저장 단위는 "묶어서 보는 단위"가 아니라 "가장 자주 다루는 단위"로 정해야 한다는 것을 배웠습니다.

CASE 01 · MIGRATION

AWS에서 GCP로의 인프라 이전

// invariant  — 인프라가 바뀌어도 서비스 동작은 동일해야 한다

DNS 전환으로 다운타임 10분 안에 이전 완료 — 이전 후 동작 차이로 인한 장애 0건

Context

회사에서 GCP 크레딧을 지원받게 되면서 운영 비용 절감을 위해 API 서버를 AWS EC2에서 GCP Compute Engine으로 이전했습니다. 데이터베이스는 이번 이전 범위에서 제외하고 애플리케이션 계층만 옮겼습니다. 성능 개선이 목적이 아니라 실행 환경만 변경하는 작업이었기 때문에, 서비스 중단 없이 기존 동작을 그대로 유지하는 것을 가장 중요한 목표로 삼았습니다.

Approach

  • 애플리케이션 계층만 이전 — 데이터베이스는 기존 위치에 두고 실행 위치만 옮겼습니다. 이전과 리팩터링을 동시에 하지 않고 변경 지점을 하나로 좁혀야, 문제가 생겼을 때 원인을 특정할 수 있기 때문입니다.
  • 사전 검증 — 옮긴 서버가 기존 데이터베이스에 정상적으로 연결되고 응답이 이전과 같은지 먼저 확인했습니다.
  • DNS 전환은 마지막에 — 새 환경에서 동작을 먼저 확인한 뒤 트래픽을 옮겨 문제 발생 시 되돌릴 수 있는 상태를 유지했습니다.

CI/CD

인계받은 서비스는 Jenkins로 배포되고 있었고, 배포를 위해 별도의 CI 서버를 계속 띄워두고 관리해야 했습니다. 빌드와 배포 과정을 GitHub Actions로 옮겨 저장소와 CI/CD 파이프라인을 한곳에서 관리하도록 통합했습니다. 별도 CI 서버를 운영할 필요가 없어졌고, 코드와 배포 파이프라인을 같은 곳에서 다루게 됐습니다.

브랜치는 main / develop으로 운영했습니다. 기능 작업은 develop에 모아 검증한 뒤 main으로 병합하고, main 기준으로만 운영 배포가 나가도록 해 배포 대상이 되는 코드를 한 브랜치로 고정했습니다.

CASE 01 · CACHING

게임 랭킹 조회의 캐시 적용

Problem

랭킹은 모든 사용자가 같은 결과를 보는 데이터인데, 조회할 때마다 집계 쿼리가 실행됐습니다. 사용자 수에 비례해 동일한 계산이 반복되는 구조였습니다.

Solution

  • 랭킹 결과를 Redis에 10분 TTL로 캐싱해, 만료 전까지는 집계 없이 응답하도록 했습니다.
  • 랭킹은 실시간성이 엄격하게 요구되지 않는 데이터라고 판단해, 최신성을 일부 포기하는 대신 부하를 줄이는 쪽을 택했습니다.
  • 이후 변경 빈도가 낮고 모든 사용자가 같은 결과를 보는 조회를 같은 기준으로 판별해 캐싱을 넓혀 적용했습니다.

What I learned

캐시는 단순히 성능을 높이는 기술이 아니라 데이터가 얼마나 최신이어야 하는지를 결정하는 설계라는 점을 배웠습니다. 이를 통해 데이터마다 허용 가능한 지연 시간이 다르다는 것을 고려하며 캐시 적용 여부를 판단하게 되었습니다.
