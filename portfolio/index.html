CASE 01

결제 중복 처리 방지와 데이터 정합성 확보

클라이언트가 보낸 결제 결과를 신뢰하지 않고 스토어 영수증을 검증해 결제 정보를 확인하고, 지급 갱신 구간을 행 락으로 직렬화해 운영 기간 중 중복 지급 0건을 유지했습니다.

역할: 영수증 검증과 지급 처리, 스토어 알림 연동의 설계와 구현

Problem

인앱결제에서 클라이언트가 전달한 결제 성공 결과를 그대로 신뢰하면 세 가지 문제가 발생할 수 있습니다.

  • 위변조 — 실제 결제 없이도 성공 결과를 조작해 서버에 전달할 수 있습니다.
  • 재전송 — 동일한 영수증을 여러 번 보내면 이미 처리한 결제라도 재화가 중복 지급될 수 있습니다.
  • 동시 요청 — 같은 영수증이 동시에 들어오면 중복 확인과 잔액 갱신 사이에서 경쟁 상태가 발생할 수 있습니다.

재전송과 동시 요청은 애플리케이션 코드로 막을 수 없습니다. 확인과 지급 사이에 다른 요청이 들어오면 두 요청 모두 미지급 상태를 확인할 수 있기 때문입니다.

Investigation

앱에서 전달되는 결과는 조작 가능하므로 신뢰하지 않고 스토어의 결제 정보를 서버에서 직접 검증한 결과를 지급의 근거로 삼도록 설계했습니다.

Architecture

Fig. 1 — 결제 검증 파이프라인

Solution

  • 서버 사이드 영수증 검증 — 앱의 결제 결과를 신뢰하지 않고 Google Play Developer API와 App Store Server API로 영수증을 서버에서 직접 검증합니다.
  • transaction_id UNIQUE 제약 — 재전송이 들어와도 DB의 UNIQUE 제약에서 차단됩니다. 애플리케이션 조건문이 아니라 스키마가 중복을 막게 했습니다.
  • 비관적 락 — 잔액 갱신 구간에 SELECT ... FOR UPDATE로 유저 행을 잠가 동시 요청을 직렬화했습니다.
  • 환불 자동 반영 — 스토어의 환불을 수신해 수기 대응 없이 서버 상태를 스토어와 정합성을 유지합니다.

Result

✅
  • 클라이언트 결과를 신뢰하지 않고 스토어에 서버 검증
  • 환불이 자동 반영되어 수기 대응 제거
  • 운영 기간 중 중복 지급 0건
CASE 02

애플리케이션 메모리 가공으로 발생한 서버 OOM

메모리가 지속적으로 증가하다가 간헐적으로 프로세스가 강제 종료되는 장애를 힙 덤프와 메모리 사용량을 비교해 원인을 추적하여 애플리케이션 메모리에서 대량의 데이터를 가공하던 구조를 DB 쿼리 레벨로 이관했습니다.

역할: 원인 추적부터 구조 개선까지 수행

Problem

운영 중 서버 메모리가 급증하며 간헐적으로 OOM Kill로 강제 종료됐습니다. 추측으로 코드를 고치는 대신 메모리를 점유하는 주체부터 특정하기로 했습니다.

Investigation

  • 의심 엔드포인트에 반복 요청 — 후보 엔드포인트를 반복 호출하며 요청 전후 메모리 변화를 비교해 메모리 증가와 연관된 요청을 좁혔습니다.
  • 메모리 덤프 분석 — 반복 호출 전후로 힙 덤프 스냅샷을 떠서 비교했습니다. 반복 호출에따라 객체가 증가했고 5회 호출 후 해당 객체들이 약 7.3MB까지 증가하는 것을 확인했습니다. LINQ 가공 과정에서 생성된 중간 객체가 반복호출과 함께 힙 점유량을 증가시키는 패턴을 확인했습니다.

Root Cause

⚠️
여러 데이터를 애플리케이션 메모리로 가져온 뒤 Join과 GroupBy로 가공하는 패턴이었습니다. 최종 응답은 작아도 가공 과정에서 중간 객체가 생성되면서 힙 점유량이 증가하는 구조였습니다.

Solution

  • 가공을 DB 쿼리 레벨로 이관 — 조인과 집계를 SQL로 옮겨 애플리케이션이 데이터를 모두 메모리에 적재하지 않고 필요한 결과만 조회하도록 변경했습니다.
  • 증설이 아니라 구조를 변경 — 메모리 증설도 선택지였지만 힙 점유가 데이터에 비례해 커지는 구조에서 증설만으로 근본적인 해결이 어렵다고 판단해 데이터 처리 구조를 바꿨습니다.

Result

✅
  • 반복 호출에 따라 증가하던 중간 객체 생성을 DB 쿼리 레벨로 이관
  • 애플리케이션에서 대량 데이터를 메모리에 올려 가공하던 구조를 제거
  • 동일 원인으로 판단한 메모리 급증 재발 없음
CASE 03

데이터 증가로 드러난 조회 성능 문제

코드 변경 없이 데이터가 증가하면서 특정 조회의 성능 문제가 드러났습니다. 실행 계획을 분석해 인덱스를 제대로 활용하지 못하는 조회 패턴을 확인하고 복합 인덱스로 바로잡았습니다.

역할: 원인 추적과 인덱스 재설계 수행

Problem

채팅 기록이 누적되면서 특정 조회의 처리 시간이 증가했습니다. 배포가 없는 기간에 나타난 증상이라 최근 변경부터 의심하는 접근이 통하지 않았습니다.

⚠️
배포 없이 데이터가 누적되는 상황에서 성능이 악화됐기 때문에 데이터 증가에 따라 비용이 커지는 조회 경로를 중심으로 원인을 좁혔습니다.

Investigation

  • 느려진 조회 특정 — 처리 시간이 길어진 요청을 기준으로 채팅 기록 조회로 대상을 좁혔습니다.
  • EXPLAIN으로 실행 계획 확인 — 해당 조회가 인덱스를 타지 못하고 전체 스캔으로 떨어진다는 것을 확인했습니다.

Root Cause

채팅 기록 조회에 필터링은 이미 걸려 있었지만 필터 조건과 ORDER BY 순서가 인덱스 컬럼 구성과 어긋나 있었습니다. 데이터가 적을 때는 전체 스캔 비용이 감당돼 드러나지 않다가 누적량이 늘어날수록 스캔 비용이 그대로 응답 지연으로 나타났습니다.

Solution

  • 조회 패턴 기준 복합 인덱스 구성 — WHERE가 항상 (user_id, character_id)로 들어오고 정렬이 created_at이었으므로 (user_id, character_id, created_at) 순서로 두어 필터와 정렬을 인덱스 하나로 커버했습니다.

Result

✅
  • EXPLAIN 기준 전체 스캔이던 조회가 인덱스 range 스캔으로 전환
  • 필터와 정렬에 맞는 복합 인덱스를 사용해 전체 데이터를 스캔하지 않고 필요한 범위를 조회
  • 데이터가 누적된 이후에도 해당 조회의 불필요한 전체 스캔을 제거
CASE 04

목록 조회의 N+1 쿼리 제거

목록 한 건마다 이미지 조회가 따로 나가던 구조를 일괄 조회 한 번으로 바꿔 DB 왕복 횟수가 목록 건수에 비례하지 않도록 만들었습니다.

역할: 조회 구조 분석과 개선 구현

Problem

목록 자체는 한 번의 쿼리로 가져오고 있었지만 각 항목의 대표 이미지를 붙이는 코드가 반복문 안에서 항목마다 이미지 테이블을 다시 조회하고 있었습니다.

  • 목록이 N건이면 쿼리가 1 + N회 실행되는 N+1 구조였습니다.
  • 개별 이미지 조회는 빠르더라도 호출 횟수가 목록 건수에 비례해 증가하면서 전체 응답 시간이 함께 증가할 수 있는 구조였습니다.

Investigation

  • 목록 건수와 쿼리 횟수의 관계 확인 — 목록 건수를 늘려가며 DB 호출 횟수가 함께 증가하는 것을 확인했습니다.
  • 반복문 내부 조회 확인 — 목록의 각 항목을 처리하는 반복문에서 이미지 조회 메서드가 호출되어 항목마다 별도의 DB 요청이 발생하는 구조를 확인했습니다.

Root Cause

⚠️
목록의 각 항목을 처리하는 반복문 내부에서 이미지 조회 메서드를 호출하고 있어 목록 건수만큼 동일한 DB 조회가 반복되는 N+1 구조였습니다. 개별 쿼리의 실행시간이 짧더라도 호출 횟수가 N에 비례하기 때문에 목록 크기가 커질수록 전체 응답 시간이 증가했습니다.

조회 패턴

Fig. 2 — 조회 패턴 변경 전후

Solution

  • 선행 수집 후 일괄 조회 — 목록에서 항목 식별자를 먼저 수집한 뒤 IN 조건으로 이미지를 한 번에 조회했습니다.
  • 해시맵으로 매핑 — 가져온 이미지를 항목 식별자로 그룹지어 맵에 담고 각 항목은 조회 없이 맵에서 꺼내 씁니다.

Result

✅
  • 이미지 조회에 따른 DB 왕복 횟수가 목록 건수와 무관하게 2회로 고정
CASE 05

요청과 실행을 분리한 AI 이미지 생성 파이프라인

요청 즉시 실행하던 약 30초짜리 외부 호출을 DB 기반 대기열로 분리해 동시 실행 수를 제한하고 작업 상태를 영속화했습니다.

역할: 파이프라인 설계와 구현 (이미지 생성 API는 사내 AI팀 제공)

Problem

AI 캐릭터 채팅과 이미지 생성처럼 생성형 AI 기능을 여럿 운영하는 서비스였습니다. 그중 이미지 생성은 사내 AI팀이 제공하는 API를 호출해 처리했으며 한 건을 처리하는 데 약 30초가 걸렸습니다. 기존에는 요청을 받으면 그 자리에서 생성 API를 호출하고 완료 후 S3에 업로드하고 응답하는 구조였습니다.

  • 요청이 들어오는 만큼 30초짜리 외부 호출이 그대로 늘어나 동시 실행 수를 제어할 수 없었습니다.
  • 진행 중인 작업 상태가 서버 메모리에만 존재해 재시작이나 예외 발생 시 작업 상태를 잃을 수 있었습니다.
  • 생성 실패가 영속적으로 기록되지 않아 실패 원인과 환불 처리의 근거가 남지 않았습니다.

Architecture

Fig. 3 — 대기열 기반 생성 파이프라인

Solution

  • 접수와 실행의 분리 — API는 생성 요청을 대기 상태로 저장하고 즉시 응답합니다. 실제 외부 API 호출은 스케줄러가 담당하도록 분리했습니다.
  • 상태의 영속화 — 생성 요청을 테이블 행으로 저장하고 상태 컬럼을 PENDING → PROCESSING → SUCCESS / FAILED로 상태를 관리해 서버 재시작 이후에도 접수된 작업과 처리 상태를 확인할 수 있도록 했습니다.
  • 동시 실행 수의 상한 — 스케줄러가 한 번에 정해진 개수만 꺼내 처리하도록 해 요청이 몰려도 외부 API 동시 호출 수는 서버가 정한 상한을 넘지 않도록 했습니다.
  • DB 대기열 선택 — 메시지 큐 도입도 검토했지만 처리량과 요구사항을 고려해 별도의 메시지 브로커 없이 DB 대기열과 스케줄러만으로 구현했습니다.

Result

✅
  • 생성 작업이 요청 처리 자원을 점유하지 않게 되어 외부 API의 지연과 장애가 다른 API로 번지지 않도록 격리
  • 요청이 몰려도 외부 API 동시 호출 수가 서버가 정한 상한을 넘지 않도록 제한
  • 재시작에도 작업이 유실되지 않고 실패 작업은 상태와 원인을 기준으로 추적할 수 있도록 개선
