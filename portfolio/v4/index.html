④ API 및 데이터 처리

주문 생성은 재고 선점 → 주문 생성 → 결제 요청 세 단계로 나누고, 각 단계가 실패했을 때 앞 단계를 되돌리는 보상 처리를 명시적으로 두었습니다. 외부 PG 호출이 포함되므로 하나의 DB 트랜잭션으로 묶을 수 없다는 전제에서 출발했습니다.

엔드포인트역할설계 포인트
POST /v1/orders주문 생성Idempotency-Key 헤더 필수. 같은 키의 재요청은 최초 결과를 그대로 반환
GET /v1/orders주문 목록커서 기반 페이지네이션. 정렬 키를 인덱스와 동일 순서로 고정
POST /v1/payments/confirm결제 승인PG 응답이 아니라 PG 서버 조회 결과를 근거로 상태 전이
POST /v1/orders/{id}/cancel주문 취소재고 복원과 환불 요청을 이벤트로 발행해 후속 처리와 분리
📌
상태 전이는 PENDING → PAID → SHIPPED 단방향으로만 허용하고, 역방향 전이는 별도의 취소 이벤트로만 발생하도록 막았습니다. 상태를 자유롭게 갱신할 수 있으면 어떤 경로로 잘못된 상태가 됐는지 추적할 수 없기 때문입니다.

  • orders.idem_key의 UNIQUE 제약이 주문 재전송을 막는 자리입니다. 조건문이 아니라 스키마가 중복을 막습니다.
  • payments.pg_tid도 같은 이유로 UNIQUE입니다. PG 웹훅이 여러 번 도착해도 결제가 두 번 반영되지 않습니다.
  • inventories.version은 낙관적 락 컬럼입니다. 재고 차감은 짧고 충돌 빈도가 예측 가능해 비관적 락 대신 선택했습니다.
  • 주문 목록 조회가 항상 (user_id, created_at)으로 들어오므로 같은 순서의 복합 인덱스를 두고 커서 페이지네이션을 적용했습니다.

⑥ 보안 및 인증

  • OAuth 2.0과 JWT — 액세스 토큰 만료를 30분으로 짧게 두고 재발급은 리프레시 토큰으로만 가능하게 했습니다. 리프레시 토큰은 Redis에 저장해 강제 로그아웃이 가능합니다.
  • 권한 검증을 서비스 계층에 — 컨트롤러에서만 검사하면 내부 호출 경로가 우회할 수 있어, 주문 소유자 확인을 서비스 진입점에 두었습니다.
  • 결제 검증은 PG 서버 조회로 — 클라이언트나 PG 리다이렉트 파라미터를 신뢰하지 않고, PG 서버에 직접 조회한 결과로만 결제를 확정했습니다.
  • 개인정보 암호화 — 수령인 연락처와 주소를 컬럼 단위로 암호화해 저장하고, 로그에는 마스킹된 값만 남겼습니다.

TROUBLESHOOTING 01 · CONCURRENCY

타임세일마다 반복되던 재고 초과 판매

문제 상황

타임세일이 열릴 때마다 재고보다 많은 주문이 승인되어, 운영팀이 수동으로 주문을 취소하고 고객에게 사과하는 일이 반복됐습니다. 코드는 재고를 조회하고 → 충분한지 확인하고 → 차감하는 순서였는데, 조회와 차감 사이에 다른 요청이 끼어들면 두 요청이 같은 재고를 보고 둘 다 통과합니다.

Fig. 4 — 재고 경합과 해결 방식
 [문제]  요청 A          요청 B
          │               │
          ├─ 재고 조회(1) │
          │               ├─ 재고 조회(1)   ← 둘 다 "1개 남음"으로 봄
          ├─ 검증 통과    │
          │               ├─ 검증 통과
          ├─ 차감 → 0     │
          │               └─ 차감 → -1      ← 초과 판매

 [해결]  Redis Lua Script 로 조회와 차감을 하나의 원자 연산으로
          │
          └─▶ DECRBY 결과가 음수면 즉시 롤백하고 실패 응답
                    │
                    ▼
          DB 재고는 낙관적 락(version)으로 최종 정합성 확인

해결 방안

문제를 “검증을 어떻게 강화할까”가 아니라 조회와 차감 사이의 틈을 어떻게 없앨까로 정리했습니다. 틈이 존재하는 한 검증 로직을 아무리 정교하게 만들어도 같은 사고가 납니다.

  • Redis Lua Script — 재고 선점을 조회와 차감이 분리되지 않는 하나의 원자 연산으로 만들었습니다. 남은 수량이 부족하면 스크립트 안에서 즉시 실패합니다.
  • DB 낙관적 락 — Redis는 선점 용도이고 최종 재고는 DB가 갖습니다. version 컬럼으로 갱신 충돌을 감지해 실패 시 재시도합니다.
  • 보상 처리 — 결제가 실패하면 선점한 재고를 되돌립니다. 되돌림이 유실되지 않도록 이벤트로 발행하고 컨슈머가 처리합니다.

개편 이후 재고 초과 판매 0건을 유지하고 있습니다. 월 3~5건 발생하던 수동 취소와 고객 응대 업무가 사라졌습니다. k6로 동일 SKU에 동시 500 요청을 넣는 시나리오를 회귀 테스트에 포함해, 이후 변경에서도 같은 결함이 재발하지 않도록 고정했습니다.
Why — 비관적 락이 아니라 Redis 원자 연산과 낙관적 락

가장 먼저 떠오른 선택지는 SELECT ... FOR UPDATE였습니다. 확실하지만 인기 상품 하나에 요청이 몰리면 그 행에 모든 트랜잭션이 줄을 서게 됩니다. 타임세일은 정확히 그 상황이라, 정합성은 지켜도 처리량이 무너집니다.

그래서 경합이 실제로 일어나는 지점을 DB 바깥으로 옮겼습니다. Redis는 단일 스레드로 명령을 처리하므로 Lua Script 안의 연산은 다른 요청과 섞이지 않습니다. DB에는 낙관적 락만 남겨 최종 정합성을 확인하게 했고, 대부분의 요청이 충돌 없이 통과하므로 재시도 비용도 낮았습니다.

다만 Redis와 DB 사이에 짧은 불일치 구간이 생깁니다. 이 구조는 재고처럼 잠깐 어긋나도 보상으로 복구 가능한 데이터에만 적용했고, 결제 금액처럼 그럴 수 없는 값은 DB 트랜잭션 안에 두었습니다.

TROUBLESHOOTING 02 · PERFORMANCE

주문 목록 조회 p99 1.8초

문제 상황

주문 목록 화면의 체감 속도가 느리다는 CS가 누적됐습니다. 평균 응답은 320ms로 나쁘지 않았지만 p99가 1.8초였고, 주문이 많은 헤비 유저일수록 심했습니다. 평균만 보면 정상으로 보이는 문제라 지표를 백분위로 나눠 보기 전까지 드러나지 않았습니다.

해결 방안

Datadog APM으로 느린 트레이스만 골라 보니 원인이 두 겹이었습니다.

  1. N+1 쿼리 — 주문 목록을 가져온 뒤 각 주문의 상품 정보를 개별 조회하고 있었습니다. 주문 20건이면 쿼리가 21번 나갑니다. QueryDSL로 필요한 컬럼만 한 번에 조회하도록 바꿨습니다.
  2. OFFSET 페이지네이션 — 뒷페이지로 갈수록 OFFSET이 커지면서 건너뛰는 행이 늘어났습니다. 정렬 기준을 (created_at, id)로 고정하고 커서 기반으로 바꿔, 페이지 번호와 무관하게 일정한 비용이 들도록 했습니다.

인덱스도 조회 조건과 순서가 어긋나 있어 (user_id, created_at DESC, id DESC)로 재설계했습니다. EXPLAIN ANALYZE로 접근 방식이 전체 스캔에서 인덱스 range 스캔으로 바뀐 것을 확인한 뒤 배포했습니다.

성과

p99 응답 시간
1.8s→240ms
요청당 쿼리 수
21회→2회
Why — 캐시를 먼저 붙이지 않은 이유

느린 조회에 캐시를 붙이는 것이 가장 빠른 처방처럼 보입니다. 하지만 주문 목록은 사용자마다 다르고 자주 바뀌는 데이터라 캐시 적중률이 낮고, 잘못 캐싱하면 결제 직후 주문이 목록에 안 보이는 더 나쁜 문제가 생깁니다.

캐시는 느린 쿼리를 감추는 도구이지 고치는 도구가 아니라고 봤습니다. 쿼리 자체를 일정한 비용으로 만든 뒤에도 부족하면 그때 캐시를 얹는 순서가 맞다고 판단했고, 결과적으로 캐시 없이 목표 응답 시간에 도달했습니다.

실시간 알림 플랫폼 구축

MAIN
전사 공통 알림 인프라 · 2025.03 – 재직 중
Kafka 이벤트 파이프라인멱등 컨슈머 대용량 발송채널 추상화장애 격리

① 프로젝트 개요

주문과 배송, 마케팅 등 여러 팀이 각자 알림 발송 코드를 중복으로 갖고 있었습니다. 푸시 하나를 보내려면 팀마다 FCM 연동을 새로 짜야 했고, 발송 실패는 어디에도 기록되지 않아 원인 파악이 불가능했습니다. 이를 전사 공통 플랫폼으로 통합하는 것이 과제였습니다.

담당 역할
이벤트 스키마 설계, Kafka 컨슈머와 발송 엔진 구현, 채널 추상화 설계 담당 (백엔드 2명 중 1명)
사용 기술
Java 17, Spring Boot 3, Kafka, Redis, MySQL, FCM, AWS SES

② 시스템 아키텍처

Fig. 5 — 알림 플랫폼 이벤트 흐름
  주문 서비스 ─┐
  배송 서비스 ─┼─▶ Kafka Topic ─▶ 알림 컨슈머 ─┬─▶ Push (FCM)
  마케팅 도구 ─┘   notification.v1   (멱등 처리) ├─▶ Email (SES)
                          │                     └─▶ SMS
                          │                              │
                    파티션 키 = user_id                   ▼
                    (사용자별 순서 보장)            발송 이력 DB
                                                   성공 / 실패 / 사유
                          │
                          ▼
                    DLQ (재처리 대상)

③ 설계에서 정한 것

  • 채널 추상화 — 발송 채널을 인터페이스로 두고 Push와 Email, SMS를 구현체로 분리했습니다. 채널이 늘어도 발송 엔진은 바뀌지 않습니다.
  • 발송 이력 필수 기록 — 성공과 실패, 실패 사유를 모두 남겼습니다. 기록되지 않은 실패는 존재하지 않는 것과 같아서 개선할 수 없습니다.
  • DLQ 분리 — 반복 실패한 이벤트는 별도 토픽으로 보내 정상 흐름을 막지 않게 했습니다.
  • 파티션 키를 user_id로 — 같은 사용자의 알림 순서를 보장하면서 사용자 간에는 병렬 처리되도록 했습니다.
TROUBLESHOOTING 03 · IDEMPOTENCY

같은 알림이 두세 번 발송되던 문제

문제 상황

배포나 컨슈머 재시작 직후 사용자가 같은 알림을 두세 번 받는다는 CS가 들어왔습니다. Kafka는 at-least-once 전달을 보장하므로, 컨슈머가 메시지를 처리하고 오프셋을 커밋하기 전에 종료되면 재시작 후 같은 메시지를 다시 받습니다. 브로커의 문제가 아니라 컨슈머가 중복을 전제로 설계되지 않은 것이 원인이었습니다.

해결 방안

이벤트마다 발행 시점에 event_id를 부여하고, 컨슈머가 발송 전에 Redis SETNX로 해당 ID의 처리 여부를 확인하도록 했습니다. 이미 처리된 ID면 발송을 건너뛰고 오프셋만 커밋합니다. Redis 장애를 대비해 발송 이력 테이블의 event_id에도 UNIQUE 제약을 두어 최종 방어선을 만들었습니다.

성과

✅
중복 발송 CS가 사라졌고, 컨슈머를 안심하고 재시작할 수 있게 되어 배포 중 알림 발송을 중단할 필요가 없어졌습니다.
Why — exactly-once를 추구하지 않은 이유

Kafka에는 트랜잭션 기반 exactly-once 옵션이 있지만, 이 경우 발송 대상이 FCM과 SES 같은 외부 시스템이라 브로커 트랜잭션 범위 밖입니다. 외부 호출까지 포함한 exactly-once는 원리적으로 불가능하다고 보고, 중복이 오는 것을 전제하고 컨슈머가 멱등하게 만드는 쪽을 택했습니다.

TROUBLESHOOTING 04 · THROUGHPUT

마케팅 대량 발송 시 컨슈머 랙 급증

문제 상황

마케팅 푸시를 한 번에 수십만 건 발행하면 컨슈머 랙이 급증해, 주문 완료 알림처럼 즉시 가야 하는 알림까지 수십 분 지연됐습니다. 긴급한 알림과 급하지 않은 알림이 같은 줄에 서 있는 것이 문제였습니다.

해결 방안

  • 토픽 분리 — 트랜잭션 알림과 마케팅 알림을 별도 토픽으로 나눠, 대량 발송이 즉시성 알림을 밀어내지 못하게 했습니다.
  • 컨슈머 그룹 분리와 파티션 증설 — 마케팅 토픽의 파티션을 늘리고 컨슈머 인스턴스를 수평 확장했습니다.
  • 발송 배치화 — FCM 멀티캐스트 API로 건당 호출을 묶어 외부 호출 횟수를 줄였습니다.

코드 리뷰

입사 당시에는 리뷰 없이 바로 merge하는 문화였습니다. 리뷰를 강제하기 전에 먼저 제 PR을 잘게 쪼개고 설명을 붙이는 것부터 시작했고, 리뷰가 부담이 아니라는 인식이 생긴 뒤 팀 규칙으로 제안해 도입했습니다. 지금은 승인 1건 없이는 merge가 불가능합니다.

테스트

외부 의존이 있는 코드는 테스트가 어렵다는 이유로 검증에서 빠져 있었습니다. Testcontainers를 도입해 실제 MySQL과 Redis, Kafka를 띄우고 통합 테스트를 작성했고, 커버리지를 PR 코멘트로 자동 게시해 줄어들면 눈에 보이게 만들었습니다.

기술 문서화

되돌리기 어려운 결정은 ADR(Architecture Decision Record)로 남깁니다. 선택한 안과 함께 탈락시킨 안과 그 이유를 적어두면, 나중에 상황이 바뀌었을 때 “왜 이렇게 했더라”를 다시 추적하지 않아도 됩니다. 재고 동시성 제어에서 비관적 락을 탈락시킨 근거도 문서로 남아 있습니다.
