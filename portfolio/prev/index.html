ACHIEVEMENT 01 · PAYMENT SECURITY · 하잉 앱

결제 중복 처리 방지와 데이터 정합성 확보

클라이언트가 보낸 결제 결과를 신뢰하지 않고 스토어 원장을 소스 오브 트루스로 삼아 위변조와 재전송을 차단하고, 지급 갱신 구간을 행 락으로 직렬화해 운영 기간 중 중복 지급 0건을 유지했습니다.

Problem

인앱결제에서 앱이 보내는 “결제에 성공했다”는 신호를 그대로 신뢰하면 세 가지 사고가 발생합니다.

  • 위변조 — 결제하지 않고도 성공 응답을 만들어 서버에 보낼 수 있습니다.
  • 재전송 — 성공한 영수증을 그대로 여러 번 보내면 지급이 반복됩니다.
  • 동시 요청 — 같은 영수증이 동시에 들어오면 중복 확인과 잔액 갱신 사이에 경쟁 상태가 생깁니다.

Investigation

문제를 “중복을 어떻게 막을까”가 아니라 결제 사실을 누가 보증하는가의 문제로 정리했습니다. 앱은 조작 가능한 실행 환경이므로 신뢰 경계 바깥이고, 지급의 근거가 될 수 있는 것은 스토어 서버의 거래 원장뿐이라고 판단했습니다.

Architecture

Client
  │  purchase token / receipt
  ▼
Payment API
  │
  ├─▶ ① 서버 사이드 영수증 검증
  │      Google Play Developer API · App Store Server API
  │
  ├─▶ ② transaction_id UNIQUE 제약 (멱등성)
  │      재전송 영수증은 DB 제약에서 차단
  │
  ├─▶ ③ SELECT ... FOR UPDATE (비관적 락)
  │      유저 행 잠금 → 지급 갱신 직렬화
  ▼
Payment DB (MySQL)
  ▲
  │  refund / cancel
  └── Google RTDN · App Store Server Notifications

Fig. 1 — 결제 검증 파이프라인

Solution

  • 서버 사이드 영수증 검증 — 앱의 결제 결과를 신뢰하지 않고 Google Play Developer API와 App Store Server API로 영수증을 서버에서 직접 검증합니다.
  • transaction_id UNIQUE 제약 — 재전송이 들어와도 DB 제약에서 차단됩니다. 애플리케이션 조건문이 아니라 스키마가 중복을 막게 했습니다.
  • 비관적 락 — 잔액 갱신 구간에 SELECT ... FOR UPDATE로 유저 행을 잠가 동시 요청에서도 순차 처리를 보장했습니다.
  • 환불 자동 반영 — Google RTDN과 App Store Server Notifications로 환불과 취소를 수신해 수기 대응 없이 서버 상태를 스토어와 정합하게 유지합니다.

Result

✅
  • 위변조와 재전송 결제를 서버에서 차단
  • Google과 Apple 결제를 동일한 검증 인터페이스로 통합해 플랫폼 분기를 결제 로직 밖으로 분리
  • 환불과 취소가 스토어 알림으로 자동 반영되어 수기 대응 제거
  • 운영 기간 중 중복 지급 0건
Why — 분산 락 대신 UNIQUE 제약과 DB 행 락
중복 방지를 DB 제약에 둔 이유

중복 방지 같은 불변식을 애플리케이션 조건문에 두면 호출 경로가 늘어날 때마다 빠뜨릴 수 있습니다. 우회할 수 없는 층에 두는 편이 안전하다고 판단해 스키마 제약을 선택했습니다.

Redis 분산 락이 아니라 DB 행 락인 이유
  • 분산 락이 필요한 상황은 여러 서버가 DB 밖의 자원을 두고 경합할 때입니다. 당시 문제는 같은 DB 행에 대한 동시 갱신이었고, 이 경합은 DB가 이미 트랜잭션으로 직렬화해 줍니다.
  • 행 락은 트랜잭션과 수명주기가 일치합니다. 커밋과 롤백에 맞춰 해제되므로 분산 락에서 신경 써야 하는 TTL 만료와 락 유실, 해제 누락 같은 실패 모드가 없습니다.
  • Redis에 락을 두면 정합성의 핵심 구간이 외부 인프라의 가용성에 의존하게 됩니다. 지켜야 할 데이터가 있는 곳에서 지키는 편이 구조적으로 단순합니다.
ACHIEVEMENT 02 · INCIDENT · 하잉 앱

반복되던 서버 OOM 장애의 원인별 대응

메모리 초과로 프로세스가 강제 종료되는 장애가 운영 중 여러 차례 발생했고 매번 원인이 달랐습니다. 증상이 아니라 원인 단위로 접근해 건마다 따로 좁혀 들어갔고, 그중 두 건을 정리했습니다.

Problem

운영 중 서버 메모리가 계속 올라가다 OOM Kill로 프로세스가 강제 종료되는 장애가 반복됐습니다. 증상은 매번 같았지만 원인은 건마다 달랐고, 공통적으로 직전 배포가 없어 배포 이력에는 단서가 없었습니다.

⚠️
같은 증상이라고 같은 원인이 아니었습니다. 한 번 고친 방법을 다음 장애에 그대로 적용할 수 없었기 때문에, 증상이 아니라 원인 단위로 매번 처음부터 좁혀야 했습니다.

공통 접근

  • 메모리를 점유하는 주체부터 특정 — 추측으로 코드를 고치지 않고, 어떤 요청과 어떤 객체가 힙을 점유하는지 먼저 확인했습니다.
  • 배포 이력이 없으면 데이터를 의심 — 코드가 그대로인데 증상이 새로 생겼다면 시간에 따라 변하는 조건, 즉 데이터 누적을 원인 축으로 잡았습니다.

사례 1 — 애플리케이션 메모리에서 하던 가공

원인 파악
  • 의심 엔드포인트에 반복 요청 — 메모리 증가와 상관관계가 있는 요청을 찾기 위해 후보 엔드포인트를 반복 호출하며 사용량 변화를 관찰했습니다.
  • 메모리 덤프 분석 — 어떤 객체가 힙을 점유하는지 덤프로 확인해 추측이 아니라 실제 점유 주체를 근거로 범위를 좁혔습니다.

여러 테이블을 각각 통째로 조회한 뒤 애플리케이션 메모리에서 Join과 GroupBy로 가공하는 패턴이었습니다. 최종 응답은 작아도 중간 단계에서 원본 데이터 전체가 힙에 올라오는 구조였습니다.

조치
  • 가공을 DB 쿼리 레벨로 이관 — 조인과 집계를 SQL에서 처리하고 서버는 이미 좁혀진 결과만 받도록 바꿨습니다. 인덱스와 옵티마이저를 쓸 수 있는 계층에서 처리하게 한 것입니다.
  • 중간 결과의 크기를 데이터 증가와 분리 — 힙에 올라오는 양이 전체 데이터량이 아니라 응답 크기에 비례하도록 만들었습니다.

사례 2 — 데이터가 쌓이면서 뒤늦게 드러난 조회 결함

원인 파악
  • 에러 로그에서 출발 — 프로세스 종료 시점의 로그를 기준으로 어떤 요청 처리 중에 발생했는지 범위를 좁혔습니다.
  • EXPLAIN으로 실행 계획 확인 — 해당 조회가 인덱스를 타지 못하고 전체 스캔으로 떨어진다는 것을 확인했습니다.

채팅 기록 조회에 필터링은 이미 걸려 있었지만, 필터 조건과 ORDER BY 순서가 인덱스 컬럼 구성과 어긋나 있었습니다. 데이터가 적을 때는 전체 스캔 비용이 감당돼 드러나지 않다가, 누적량이 임계를 넘은 시점에 한 번의 요청이 방대한 행을 메모리에 올리면서 장애로 나타났습니다.

조치
  • 조회 패턴 기준 복합 인덱스 구성 — WHERE가 항상 (user_id, character_id)로 들어오고 정렬이 created_at이었으므로 (user_id, character_id, created_at) 순서로 두어 필터와 정렬을 인덱스 하나로 커버했습니다.
  • 조회량의 상한을 서버가 결정 — 목록 조회는 요청이 요구하는 만큼이 아니라 서버가 정한 상한 안에서 응답하도록 했습니다.
  • 필요한 곳에만 — 인덱스는 쓰기 비용을 늘리므로 실제 조회 패턴이 확인된 컬럼에만 적용했습니다.

Result

✅
  • 두 건 모두 동일 원인의 OOM이 재발하지 않았고 서버 메모리 사용량이 안정화
  • 사례 2는 EXPLAIN 기준 접근 방식이 전체 스캔에서 인덱스 range 스캔으로 전환
  • 데이터가 늘어도 해당 요청이 점유하는 메모리가 그에 비례해 늘지 않게 됨
Why — 증상이 같아도 원인은 다르다

두 건 모두 “메모리 초과로 인한 프로세스 종료”라는 같은 증상이었지만, 하나는 가공하는 계층의 문제였고 다른 하나는 인덱스와 조회 패턴의 문제였습니다. 증상에 이름을 붙여 대응하면 다음 건에서도 같은 곳만 들여다보게 됩니다. 그래서 매번 무엇이 힙을 점유하는가부터 다시 확인했고, 그 확인은 감이 아니라 덤프와 EXPLAIN으로 했습니다.

두 건에서 공통으로 얻은 것은 메모리를 결정하는 것이 데이터의 총량이 아니라 그것을 다루는 방식이라는 점입니다. 그래서 이후로는 “지금 정상 동작하는가”보다 “데이터가 100배가 돼도 같은 비용으로 동작하는가”를 함께 확인하게 됐습니다.

ACHIEVEMENT 03 · DB TUNING · 하잉 앱

간헐적 API 응답 지연과 InnoDB 버퍼 풀 증설

간헐적으로 수 초씩 걸리던 응답의 원인을 쿼리가 아닌 DB 서버 설정에서 찾아, 서비스 중단 없이 버퍼 풀을 증설해 콜드 쿼리 지연과 앱 첫 진입 로딩 지연을 해소했습니다.

Problem

API 응답이 간헐적으로 수 초씩 지연되고 앱을 처음 실행할 때의 로딩도 유독 느리다는 증상이 있었습니다. 느린 쿼리를 의심했지만 같은 쿼리를 다시 실행하면 정상 속도로 돌아왔습니다. 느린 쿼리라기보다 같은 쿼리가 어떤 때는 느리고 어떤 때는 빠른 문제였습니다.

Investigation

  • 재현 조건에서 출발 — 처음 실행되거나 오랜만에 실행되는 쿼리만 느리고 직후 재실행은 빠르다는 패턴을 확인했습니다. 쿼리 자체가 아니라 데이터를 어디서 읽어오는지의 차이라고 판단했습니다.
  • 디스크 읽기 병목 의심 — 첫 실행은 디스크에서, 재실행은 메모리에서 읽는다면 증상이 정확히 설명됩니다. InnoDB 버퍼 풀 설정을 확인했습니다.
  • 기본값 그대로 운영 중 — 버퍼 풀이 MySQL 기본값 128MB로 운영되고 있었습니다. 누적된 데이터 대비 턱없이 작아 자주 읽는 데이터조차 메모리에 머물지 못하고 매번 디스크로 밀려나는 상태였습니다.

Root Cause

⚠️
DB를 관리형 서비스가 아니라 EC2에 직접 구성해 운영했기 때문에 스키마와 인덱스뿐 아니라 DB 서버의 설정과 자원도 직접 관리 대상이었고, innodb_buffer_pool_size가 기본값으로 남아 있었습니다.

Solution

  • 인스턴스 메모리 사전 확인 후 증설 — DB가 EC2에서 직접 운영 중이었으므로 서버의 가용 메모리를 먼저 확인하고 애플리케이션과 OS 몫을 제외한 범위에서 5GB로 잡았습니다.
  • 서비스 중단 없이 적용 — innodb_buffer_pool_size는 동적 변경이 가능한 파라미터라 재시작 없이 반영하고, 재부팅 이후에도 유지되도록 설정 파일에 함께 기록했습니다.

Result

✅
  • 간헐적으로 수 초씩 걸리던 콜드 쿼리 지연과 앱 첫 진입 로딩 지연 해소
  • 자주 읽는 데이터가 메모리에 머물게 되어 같은 쿼리의 응답 시간이 실행 시점과 무관하게 일정해짐
  • 서비스 중단 없이 적용
Why — 쿼리를 고치지 않고 설정을 본 이유

같은 쿼리의 첫 실행과 재실행이 다르게 동작한다면 의심할 곳은 SQL이 아니라 데이터가 어느 계층에서 읽히는가입니다. 쿼리를 튜닝해도 디스크에서 읽는다는 사실은 바뀌지 않습니다.

DB의 기본 설정은 운영 데이터 규모를 알지 못합니다. 그래서 기본값으로 남아 있는 설정 자체가 점검 대상이라고 보고, 인스턴스 메모리를 먼저 확인한 뒤 동적 변경이 가능한 파라미터를 골라 무중단으로 반영했습니다.

ACHIEVEMENT 04 · ASYNC PIPELINE · 하잉 앱

요청과 실행을 분리한 AI 이미지 생성 파이프라인

요청 즉시 실행하던 30초짜리 외부 호출을 대기열로 옮겨 동시 실행 수의 상한을 서버가 정하고, 재시작에도 작업이 유실되지 않도록 전환했습니다.

Problem

이미지 생성은 사내 AI팀이 제공하는 API를 호출해 처리했고 한 건에 30초 정도가 걸렸습니다. 요청을 받으면 그 자리에서 생성 API를 호출하고 완료되면 S3에 업로드한 뒤 소켓으로 알리는 구조였습니다. 클라이언트는 기다리지 않았지만 서버 쪽에는 문제가 남아 있었습니다.

  • 요청이 들어오는 만큼 30초짜리 외부 호출이 그대로 늘어나 동시 실행 수에 상한이 없었습니다. 스레드와 커넥션이 묶이고 외부 API 호출 제한에도 걸립니다.
  • 진행 중인 작업이 서버 메모리에만 존재해 재배포나 재시작, 예외가 나면 그대로 사라졌습니다. 사용자는 완료 알림을 받지 못합니다.
  • 실패가 어디에도 기록되지 않았습니다. 무엇이 왜 실패했는지 알 수 없으니 후속 처리의 근거도 남지 않습니다.

Architecture

[접수]  API ──▶ 요청을 PENDING 으로 저장하고 즉시 응답
                        │
[실행]  Scheduler ──▶ 정해진 개수만 조회 (동시 실행 상한)
                        │
                  PENDING → PROCESSING
                        │
                  외부 생성 API 호출 (약 30초)
                        │
              ┌─────────┴─────────┐
              ▼                   ▼
            DONE                FAILED
       S3 업로드 · 소켓 알림    환불 처리 · 원인 기록

Fig. 2 — 대기열 기반 생성 파이프라인

Solution

  • 접수와 실행의 분리 — API는 생성 요청을 대기 상태로 저장만 하고 끝냅니다. 실제 호출은 스케줄러가 담당합니다.
  • 상태를 저장소에 남김 — PENDING → PROCESSING → DONE / FAILED로 관리해 서버가 중간에 내려가도 재시작 후 이어서 처리할 수 있게 했습니다.
  • 동시 실행 수의 상한 — 스케줄러가 한 번에 정해진 개수만 꺼내 처리합니다. 요청이 몰려도 외부 API 동시 호출 수는 서버가 정한 값을 넘지 않습니다.
  • 실패의 후속 처리 — 생성 실패는 다시 시도하지 않고 환불로 처리했습니다. 대상을 특정할 수 있어야 하므로 실패도 결과의 한 종류로 기록했습니다.

Result

✅
  • 생성 작업이 요청 처리 자원을 점유하지 않게 되어 외부 API의 지연과 장애가 다른 API로 번지지 않도록 격리
  • 요청이 몰려도 외부 API 동시 호출 수가 서버가 정한 상한을 넘지 않음
  • 서버가 재시작돼도 대기 중이거나 처리 중이던 요청이 남아 있어 작업이 유실되지 않음
  • 실패한 작업이 상태로 남아 환불 처리와 원인 파악이 가능
Why — 메시지 큐 대신 DB 테이블과 스케줄러

처음에는 메시지 큐 도입을 먼저 떠올렸지만 필요 조건을 따져보며 DB 기반 대기열로 방향을 잡았습니다.

  • 필요한 것은 버퍼링과 순차 처리, 실패 기록, 상태 조회였습니다. 이 중 “지금 어떤 작업이 어떤 상태인가”를 들여다보는 운영 가시성은 SQL로 바로 조회되는 DB가 브로커보다 낫습니다.
  • 소비자가 스케줄러 하나뿐이고 처리량도 낮아 큐가 강점을 갖는 다중 컨슈머 분배나 고처리량 상황이 아니었습니다. 이 조건에서 브로커는 성능 이점 없이 운영과 모니터링, 장애 지점만 추가합니다.
  • 작업 상태가 서비스 데이터와 같은 DB에 있어 접수와 상태 기록을 하나의 트랜잭션으로 다룰 수 있었습니다.
ACHIEVEMENT 05 · QUERY OPTIMIZATION · 하잉 앱

목록 조회의 N+1 쿼리 제거

목록 한 건마다 이미지 조회가 따로 나가던 구조를 일괄 조회 한 번으로 바꿔, DB 왕복 횟수가 목록 건수에 비례하지 않도록 만들었습니다.

Problem

목록 API가 느리다는 제보가 있었습니다. 목록 자체는 한 번의 쿼리로 가져오고 있었지만, 각 항목의 대표 이미지를 붙이는 코드가 반복문 안에서 항목 한 건마다 이미지 테이블을 다시 조회하고 있었습니다.

  • 목록이 N건이면 쿼리가 1 + N회 나갑니다. 개별 쿼리는 각각 빠르므로 느린 쿼리를 찾는 방식으로는 원인이 잡히지 않습니다.
  • 지연이 데이터의 총량이 아니라 한 화면에 보여주는 건수에 비례합니다. 목록을 더 많이 내려줄수록 선형으로 느려집니다.
  • 요청 하나가 커넥션을 잡고 왕복을 반복하므로 요청이 몰릴 때 커넥션 점유 시간이 함께 늘어납니다.

Investigation

  • 비례 관계부터 확인 — 특정 데이터에서만 느린 것이 아니라 목록 건수를 늘릴수록 응답이 함께 늘었습니다. 쿼리 한 번의 비용이 아니라 횟수가 비용이라고 판단했습니다.
  • 정렬과 상위 1건 추출의 위치 — OrderByDescending과 FirstOrDefault가 await 뒤에 붙어 있었습니다. DB가 아니라 애플리케이션에서 동작하므로, 한 건만 쓰면서 해당 항목의 성공 이미지를 전부 전송받고 있었습니다.
  • 인덱스 확인 — 조회 조건이 (항목 식별자, 상태)이고 정렬이 등록일시였으므로 이 순서의 복합 인덱스가 있는지 함께 점검했습니다.

Root Cause

⚠️
조건식을 받아 즉시 실행하는 조회 메서드를 반복문 안에서 호출하면 호출 한 번이 그대로 DB 왕복 한 번이 됩니다. 코드 한 줄이라 비용이 드러나지 않지만, 실제 비용은 그 줄이 아니라 그 줄을 감싼 반복문이 결정합니다.

조회 패턴

[변경 전]  목록 조회 1회
             │
             └─▶ for each (N건)
                    └─▶ 이미지 조회 ──▶ DB      총 1 + N회
                         (전체 수신 후 메모리에서 정렬·1건 선택)

[변경 후]  목록 조회 1회
             │
             └─▶ 식별자 수집 ──▶ IN 일괄 조회 1회 ──▶ DB   총 2회
                    │
                    └─▶ 메모리에서 Dictionary 매핑 (건별 O(1))

Fig. 3 — 조회 패턴 변경 전후

Solution

  • 선행 수집 후 일괄 조회 — 목록에서 항목 식별자를 먼저 모으고 IN 조건으로 이미지를 한 번에 가져왔습니다. 왕복이 목록 건수와 분리됩니다.
  • 딕셔너리로 매핑 — 가져온 이미지를 항목 식별자로 그룹지어 사전에 담고, 각 항목은 조회 없이 사전에서 꺼내 씁니다.
  • 조회 대상 좁히기 — 성공 상태 조건을 일괄 조회에 그대로 걸고, 최신 한 건 선택은 그룹 안에서 처리했습니다.
  • 인덱스 정렬 — (항목 식별자, 상태, 등록일시) 순서의 복합 인덱스로 필터와 정렬을 인덱스 하나로 커버하게 했습니다.
  • 식별자 개수의 상한 — IN 목록이 커지면 파라미터 한계에 걸리므로, 목록 크기를 서버가 정한 상한 안에서만 다루도록 두었습니다.

Result

✅
  • DB 왕복이 1 + N회에서 2회로 고정되어 목록 건수와 무관해짐
  • 목록을 더 많이 내려줘도 응답 시간이 건수에 비례해 늘지 않음
  • 요청 하나가 커넥션을 잡고 있는 시간이 줄어 동시 요청 상황에서의 여유 확보
Why — 조인 한 번이 아니라 일괄 조회 두 번

한 번의 쿼리로 끝내는 조인을 먼저 검토했지만, 항목 하나에 이미지가 여러 건이라 조인하면 항목 정보가 이미지 수만큼 중복되어 전송됩니다. 필요한 것은 항목당 대표 한 건뿐이었습니다. DB에서 항목별 최신 한 건만 뽑는 방법도 있지만 쿼리가 복잡해지는 데 비해, 이 문제의 비용은 쿼리의 정교함이 아니라 왕복 횟수에 있었습니다. 두 번으로 줄이면 목적은 달성됩니다.

같은 목록 조회라도 실패하는 방식이 다르다

앞선 OOM 사례가 한 번에 너무 많이 읽어서 생긴 문제였다면, 이번은 조금씩 너무 여러 번 읽어서 생긴 문제였습니다. 전자는 한 요청이 점유하는 메모리가, 후자는 한 요청이 만드는 왕복 횟수가 데이터에 따라 커집니다. 그래서 목록을 다루는 코드에서는 응답 크기뿐 아니라 이 코드가 만드는 쿼리가 몇 번인지를 함께 보게 됐습니다.

ACHIEVEMENT 06 · MIGRATION & CI/CD · NFC 콘텐츠

AWS에서 GCP로 API 서버 이전과 배포 파이프라인 통합

실행 환경만 옮기는 작업으로 범위를 좁히고 DNS 전환을 마지막에 두어 이전 후 동작 차이로 인한 장애 없이 이전을 완료하고, Jenkins 기반 배포를 GitHub Actions로 통합했습니다.

Background

회사에서 GCP 크레딧을 지원받게 되면서 운영 비용 절감을 위해 API 서버를 AWS EC2에서 GCP Compute Engine으로 이전했습니다. 성능 개선이 목적이 아니라 실행 환경만 변경하는 작업이었기 때문에 서비스 중단 없이 기존 동작을 그대로 유지하는 것을 가장 중요한 목표로 삼았습니다.

Migration Strategy

  1. 애플리케이션 계층만 이전 — 데이터베이스는 기존 위치에 두고 실행 위치만 옮겼습니다.
  2. 새 환경 구성 — GCP Compute Engine에 동일한 런타임과 Nginx 구성을 올렸습니다.
  3. 사전 검증 — 옮긴 서버가 기존 데이터베이스에 정상적으로 연결되고 응답이 이전과 같은지 먼저 확인했습니다.
  4. DNS 전환은 마지막에 — 도메인은 그대로 두고 레코드가 가리키는 주소만 새 서버로 바꿔 프론트 수정 없이 트래픽을 옮겼고 문제 발생 시 되돌릴 수 있는 상태를 유지했습니다.

CI/CD 통합

인계받은 서비스는 Jenkins로 배포되고 있었고 배포를 위해 별도의 CI 서버를 계속 띄워두고 관리해야 했습니다. 빌드와 배포 과정을 GitHub Actions로 옮겨 저장소와 파이프라인을 한곳에서 관리하도록 통합했습니다. 브랜치는 main과 develop으로 운영해 기능 작업은 develop에 모아 검증한 뒤 main으로 병합하고, main 기준으로만 운영 배포가 나가도록 배포 대상 코드를 한 브랜치로 고정했습니다.

Result

✅
  • 이전 이후 기능 차이나 운영 장애 없이 서비스를 안정적으로 유지
  • 되돌릴 수 있는 상태를 유지한 채 전환
  • 크레딧 지원을 활용해 API 서버 운영 비용 절감
  • 별도 CI 서버 운영이 필요 없어져 서버 한 대와 그 관리 부담을 함께 제거
Why — 이전과 개선을 동시에 하지 않은 이유

이전과 리팩터링을 함께 하면 문제가 생겼을 때 원인이 인프라인지 코드인지 가릴 수 없습니다. 변경 지점을 하나로 좁혀야 원인을 특정할 수 있어서, 개선 욕심을 접고 데이터베이스는 이전 범위에서 제외했습니다.

DNS 전환을 마지막에 둔 것도 같은 이유입니다. 새 환경을 먼저 검증하고 트래픽만 옮기면, 문제가 생겼을 때 되돌리는 비용이 레코드 원복 하나로 끝납니다.

데이터는 성격에 따라 MySQL(핵심 데이터)와 Redis(캐시), MongoDB(채팅 로그)로 나누고 이미지는 S3에 저장했습니다. DB는 관리형 서비스가 아니라 EC2에 직접 구성해 운영했기 때문에 스키마와 인덱스뿐 아니라 DB 서버의 설정과 자원도 직접 관리 대상이었고, Achievement 02와 03이 이 조건에서 나온 문제입니다.

설계 결정

채팅 로그 저장소로 MongoDB

회원과 캐릭터 조합마다 끝없이 누적되는 채팅 로그의 저장소로 MySQL과 MongoDB가 후보였습니다.

  • 조회가 항상 대화 단위로 들어오고 다른 테이블과의 조인이 필요 없는, 읽기 패턴이 단순한 데이터였습니다.
  • 메시지에 텍스트와 이미지, 시스템 메시지 등 형태가 다른 필드가 섞이고 스키마 변경이 잦아 문서 모델이 자연스러웠습니다.
  • 쓰기가 append 위주인 로그성 데이터를 분리해 핵심 트랜잭션 데이터가 있는 MySQL의 부하와 격리했습니다.
클라이언트가 언어를 관리하지 않는 다국어 응답 구조

앱과 웹, 백오피스가 각자 번역을 관리하면 서버가 새 에러 코드를 추가할 때마다 모든 클라이언트 배포가 필요해지고, 번역이 누락되면 사용자에게 코드값이 그대로 노출됩니다. 서버에서 처리하더라도 메시지를 반환하는 모든 지점이 언어 분기를 갖게 되면 같은 문제가 코드 안으로 옮겨올 뿐입니다.

  • 미들웨어에서 언어를 한 번만 판별 — Accept-Language 헤더를 요청 진입 지점에서 해석해 이후 컨트롤러와 서비스는 언어를 알 필요가 없게 했습니다.
  • 번역 테이블을 단일 소스로 — 메시지를 코드가 아니라 데이터로 관리해 문구 수정과 지원 언어 추가를 코드 변경 없이 처리할 수 있게 했습니다.
  • 조회 캐싱 — 거의 모든 응답에서 조회되는 데이터라 매 요청 DB를 거치지 않도록 캐싱했습니다. 대신 수정 반영에 캐시 갱신만큼의 시차가 생깁니다.
  • 기본 언어 폴백 — 헤더가 없거나 미지원 언어여도 코드값이 그대로 노출되지 않게 했습니다.

결과 — 세 클라이언트가 동일한 메시지 소스를 참조하게 되어 문구 수정과 지원 언어 추가가 클라이언트 배포 없이 번역 테이블 수정만으로 반영됩니다. 다국어는 번역 파일을 만드는 일이 아니라 어느 계층이 언어를 책임질지 정하는 설계 문제였습니다.

운영 자동화 — 어드민 백오피스

운영팀의 반복적인 데이터 조회와 수정 요청이 개발자에게 지속적으로 전달됐습니다. 운영팀이 직접 콘텐츠와 회원 데이터를 관리할 수 있는 백오피스를 개발해 반복성 운영 요청이 개발자를 거치지 않고 처리되는 환경을 만들었고, 운영 과정의 개발 의존도를 낮췄습니다.

05Engineering Principles

01. 데이터 정합성을 우선합니다

기능이 정상적으로 동작하는 것뿐 아니라 동시에 여러 요청이 들어왔을 때도 올바른 상태를 유지하는 것을 중요하게 생각합니다. 중복을 막는 불변식은 애플리케이션 조건문보다 우회할 수 없는 층에 두는 편을 택합니다.

02. 문제의 원인을 먼저 확인합니다

단순히 코드를 수정하기보다 로그와 메모리 덤프, 실행 계획, 재현 조건을 통해 원인을 확인한 후 해결 방법을 선택합니다. 증상이 같아도 원인은 다를 수 있으므로 증상이 아니라 원인 단위로 확인합니다.

03. 운영 환경을 고려합니다

개발 환경에서 동작하는 코드보다 실제 운영 환경에서 안정적으로 동작하고 관리할 수 있는 시스템을 지향합니다. 변경은 되돌릴 수 있는 상태를 유지한 채 진행하고, 기술 선택에는 언제 다른 선택으로 넘어갈지의 기준을 함께 정해둡니다.
